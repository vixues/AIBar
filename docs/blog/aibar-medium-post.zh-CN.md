# 超越聊天框：为 AI Agent 设计安全的操作界面

*构建上下文感知操作栏 AIBar 时，我们学到了什么*

![位于聊天输入框上方的 AIBar](./assets/aibar/01-hero-aibar-dock.png)

第一代 AI 产品几乎都围绕对话展开：用户输入请求，模型返回文本，所有结果都试图塞进这一问一答之中。

Agent 的出现改变了这种界面。

Agent 的能力不止于回答问题。它会调用工具、请求权限、生成文件、打开交互式视图、运行工作流，并提出下一步建议。每项能力都会带来新的控件：允许、拒绝、停止、打开、导出、重试、检查、继续。

大多数产品会就近添加控件：哪里先需要，就先放在哪里。久而久之，操作入口散落在输入框、对话记录、权限卡片、画布工具栏和侧边栏中。模型可以告诉用户下一步做什么，界面却没有一个统一的位置让用户直接执行。

为了解决这个问题，我们构建了 **AIBar**：在聊天输入框上方放置一条常驻、能感知上下文的操作栏。目标很明确——把当前可用的操作摆到用户眼前，同时不让 Agent 接管界面。

它的交互思路来自 Apple Touch Bar：在一条紧凑的控制带上，按当前场景调整控件。AIBar 把这一模式带到 Agent 界面中，并补上来源标识、安全确认，以及操作栏之外的备用入口。

真正做起来后，我们发现这不只是工具栏的实现问题，更涉及策略、协议、布局和信任边界。

## 在对话之外增加一个操作层

对话记录适合解释过程、保存结果，却不适合承担所有操作。

当 Agent 生成报告时，对话记录负责说明结果，操作栏则提供“打开报告”。当工具需要权限时，对话记录可以保留审批信息，操作栏直接给出“允许”和“拒绝”。当生成式界面处于活动状态时，操作栏还可以提供“聚焦”“截图”和“导出”。

这样，产品就有了两个分工明确、彼此配合的层次：

- **对话层**：承载意图、过程说明和结果
- **操作层**：整理并展示当前可用的操作

AIBar 不会取代输入框，也不会取代消息中的交互内容。它只是给原本散落在各处的操作提供一个固定位置。

![输入框控制模式与输入辅助模式](./assets/aibar/02-chrome-vs-input-mode.png)

这一划分也带来一条重要的架构约束：任何一方都不能独占整条操作栏。

发送、停止、模型选择和审批等关键控件由宿主应用管理；画布、文件等当前界面可以加入自己的操作；Agent 可以发布少量与任务相关的下一步；建议引擎则负责提供低风险预测。

这些内容最终都要争取同一块有限空间。

## 内核负责决策，React 负责渲染

我们的第一个重要决定，是把操作策略与 UI 框架代码分离。

```text
protocol       条目规范、校验、标识符和传输消息
core           ContextHub、解析器、内核、WireIngress 和宿主适配接口
intent         可选的启发式建议引擎
renderer-dom   DOM 测量、渲染和指针交互
react          界面挂载
host           产品侧状态同步、操作白名单和确认流程
```

宿主先向 `ContextHub` 注册数据提供方。状态失效后，`ContextHub` 会合并短时间内的更新，主动读取当前路由、输入框模式、可用的生成式界面和待处理审批等元数据，再生成只读快照，并用持续递增的版本号记录变化。

DOM 后端先测量可用空间，内核再决定显示哪些条目、如何布局，最后由后端更新界面。React 只负责挂载和接入宿主应用，不参与排序和布局决策。

这种分层带来了三个直接收益。

第一，操作模型可以脱离浏览器进行测试。第二，不同渲染器可以共享同一套协议和解析器。第三，产品规则不会被组件的排列顺序暗中左右。

![AIBar 架构分层](./assets/aibar/04-architecture-layers.png)

静态工具栏可以先把内容画出来，再用 CSS 隐藏放不下的部分；上下文感知操作栏却不能这样做。解析器必须在绘制前弄清优先级、来源、安全级别，以及每项操作是否仍有可访问的备用入口。

## 把 Agent 输出当作不可信输入

允许 Agent 发布操作后，一个很自然的捷径是让模型直接生成组件或 HTML 片段。

但 AIBar 没有采用这种做法：它只接受数据，不接受可执行的界面代码。

Agent 发布的每项操作，都是一份需要经过校验的数据：

```json
{
  "id": "agent.aibar.button.open-report",
  "type": "button",
  "labelKey": "Open report",
  "effect": "read",
  "parity": "chat:link-in-reply",
  "action": {
    "name": "open_file",
    "params": {
      "fileId": "<file id>"
    }
  }
}
```

宿主应用决定如何渲染这些数据，也负责判断对应操作当前是否可用。传输内容不能包含 JavaScript、React 组件、自定义渲染函数或任意事件处理器。凡是能够携带进程内代码的条目类型，都不会开放给 Agent。

这既是安全边界，也是产品边界。无障碍体验、视觉一致性、本地化、确认流程和备用入口，始终由宿主应用负责。

接入层会自动标记 Agent 控件的来源，并在界面中明确显示。用户应该一眼看出哪些操作来自 Agent，哪些是产品原生控件。

## 把安全设计进协议

与其根据按钮文案猜测风险，不如把安全信息直接写进条目协议。

条目可以用 `effect` 字段标记操作级别：

- `read`
- `write`
- `destructive`

审批条目必须明确填写操作级别。Agent 发起的破坏性操作必须经过宿主应用确认或审批；普通建议只允许 `read` 和 `write`。

每个条目还必须声明 **parity**，也就是在 AIBar 之外完成同一操作的入口。例如，“打开报告”按钮可以对应助手回复中的文件链接，审批按钮可以对应一张常驻的权限卡片。LeAgent 目前只在聊天路由挂载 AIBar，而且视口宽度低于 640px 时不会显示，因此备用入口不是锦上添花，而是协议的一部分。

这样，AIBar 始终只是快捷入口，不会成为使用某项功能的唯一途径。

## 布局是一种资源分配

横向空间有限，不可能同时展示所有操作，因此布局本质上是在分配稀缺位置。

解析器会：

1. 按显示条件和有效期过滤条目，再判断是否可用
2. 对符合条件的固定操作排序
3. 根据实际测得的宽度安排位置
4. 通过滞回机制和短暂保留时间减少闪烁
5. 把放不下的固定操作移入溢出菜单

固定操作和预测建议走两条独立通道。建议必须达到置信度阈值，数量也有上限，而且只会使用固定操作排完后的剩余空间。因此，它们不会挤掉发送、停止、审批或其他宿主控件；放不下的建议会直接省略。

![双通道解析器](./assets/aibar/09-dual-lane-resolver.png)

这个区别看似细微，却很重要。如果预测操作与必要控件直接竞争，界面越“智能”，反而可能越不可靠。即使上下文不断变化，用户仍然需要一些位置稳定、随时找得到的关键控件。

操作栏可以随场景变化，但不能让用户觉得毫无规律。

## 一个容易被忽略的指针事件问题

我们遇到过一个很典型的问题：按钮偶尔会像失灵一样，没有任何反应。

AIBar 会频繁重新计算界面。输入框焦点变化、Agent 流式事件或布局测量，都可能触发一次更新。一次点击过程中，可能发生以下情况：

1. 用户按下某个条目，浏览器触发 `pointerdown`。
2. 此时上下文变化，界面开始更新。
3. 渲染器替换原来的 DOM 节点。
4. 浏览器无法再把预期的兼容性 `click` 发给原节点。

用户看到的结果，就是按钮“没反应”。

我们的做法是：在 `pointerdown` 时记住目标，在 `pointerup` 时执行操作，同时忽略随后多余的兼容性 `click`。另外再用移动阈值区分点击和横向拖动。

![指针事件待触发序列](./assets/aibar/08-pointer-arming-diagram.png)

这件事带来的启示是：上下文感知操作栏不是传统的静态工具栏，而是一个会持续更新的小型 UI 系统。即使 DOM 在手势中途发生变化，用户的这次操作也不能丢。

## 只同步必要信息，不复制状态

消息草稿始终由聊天输入框管理，AIBar 不会另存一套草稿状态。

输入框只把回调和少量必要信息同步给 AIBar。AIBar 可以触发发送或调整推理强度，但不会接管草稿。

为了生成本地输入建议，输入框会通过专用桥接接口提供光标前最多 32 个字符，而不是完整草稿。这段内容不会进入 `ContextHub`，共享上下文中也不会出现消息正文。

我们还发现，只看焦点并不能可靠地切换模式。打开表情面板或行内推理选择器时，焦点会短暂离开文本框。如果没有额外处理，用户还在操作，界面就可能提前切回空闲状态。为此，展开的控件会在短暂失焦期间继续保持，避免界面来回跳动。

好的数据同步约定，应该只提供对方真正需要的信息，而不是把整套状态复制过去。

## 不变量比功能更有价值

随着条目类型不断增加，我们发现最重要的不是继续堆功能，而是守住几条设计约束：

1. 每个条目都有备用入口，或明确说明为何例外。
2. Agent 传输载荷只能包含数据。
3. 核心策略与 React、DOM 保持独立。
4. 稳定标识符一经发布便不再改变，并且必须全局唯一。
5. 建议不得挤占确定性操作。
6. Agent 来源必须始终可见。
7. 由 Agent 触发的破坏性操作必须经过人工确认。
8. 不合法的 Agent 数据会被安全拒绝，不能拖垮整个操作栏。

这些规则也为后续功能划清了边界。一个新条目能渲染出来，并不代表它已经完成；还必须定义标识、来源、安全级别、备用入口，以及如何参与空间分配。

这正是“堆一组控件”和“设计一套操作协议”的区别。

## 如果再做一个 Agent 产品

如果明天要从头构建另一个 Agent 界面，我们仍会保留五项原则：

**把说明与操作分开。**让对话记录负责解释，再给操作一个独立位置。

**让宿主掌握控制权。**Agent 应通过严格协议表达要做什么，而不是直接编写可执行 UI。

**把信任边界写进协议。**接入层负责标记来源，条目协议负责声明操作级别。

**优先保证固定控件。**预测可以增加便利，但不能影响基本操作的稳定性。

**始终保留备用入口。**上下文操作栏应该提高效率，而不能成为隐藏的唯一入口。

## 为 Agent 补上操作层

Agent 界面正在走出聊天框，但这并不意味着要放弃对话。对话仍然非常适合表达意图、解释过程和理解结果。

真正缺少的是一个操作层：把模型建议、宿主能力和当前任务中的可用操作统一整理出来。

AIBar 就是我们对这一层的尝试。它已经作为独立引擎开源，并集成到 LeAgent：

- [AIBar 项目仓库](https://github.com/vixues/AIBar)
- [LeAgent 项目仓库](https://github.com/vixues/LeAgent)

核心理念很简单：Agent 可以提出下一步，规则由宿主应用制定，最后做决定的始终是用户。
